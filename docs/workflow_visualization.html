Overview

This document describes the current LangGraph workflow-based agent system for the Hospital AI Assistant. The system uses a hybrid workflow pattern with explicit nodes for predictable execution, while maintaining conversational flexibility through LLM nodes.

Implementation: Based on backend/src/agents/workflow_agent.py with 16 explicit workflow nodes.

Key Features:

  • Hybrid workflow pattern: Explicit nodes for predictable execution
  • 16 workflow nodes: route_entry, extract_patient_info, validate_info, ask_for_missing, verify_patient, create_patient, fetch_history, show_history, understand_request, validate_request, ask_for_request_info, find_doctors, inform_no_doctors, rank_doctors, create_tickets, confirm_booking
  • LLM nodes for extraction, understanding, and formatting (8 nodes use LLM)
  • Tool nodes for database operations (5 nodes call tools)
  • PostgresSaver checkpointer for state persistence (automatic after each node)
  • LangSmith integration for observability and tracing

Execution Flow:

  1. Conversation API receives message → calls graph.ainvoke(initial_state, config)
  2. LangGraph Engine loads state from PostgresSaver checkpointer (if exists)
  3. Executes nodes sequentially based on routing logic
  4. Saves checkpoint after each node execution
  5. Returns final state with all messages

System Architecture

Architecture Overview

The system consists of multiple layers matching the actual implementation in workflow_agent.py:

  • Client Layer: Frontend React App → REST API Endpoints (FastAPI)
  • Application Layer: Conversation API (routes/conversations.py) → Workflow Agent (workflow_agent.py)
  • LangGraph Layer: StateGraph Engine with 16 workflow nodes, PostgresSaver Checkpointer for state persistence
  • Node Types:
    • LLM Nodes: extract_patient_info, show_history, ask_for_missing, understand_request, ask_for_request_info, inform_no_doctors, rank_doctors, confirm_booking
    • Validation Nodes: validate_info, validate_request
    • Tool Nodes: verify_patient, create_patient, fetch_history, find_doctors, create_tickets
  • Tool Layer: Extraction Tools, Patient Tools, Doctor Tools, Ticket Tools (called from nodes)
  • LLM Services: ChatOpenAI (gpt-4o-mini) with Structured Output (Pydantic models)
  • Database Layer: PostgreSQL with patients, service_persons, tickets, conversations, checkpoints tables
  • Observability: LangSmith integration for tracing all LLM calls and workflow execution

State Management Flow

State Persistence

The workflow uses PostgresSaver checkpointer for state persistence:

  • State is persisted after each node execution
  • Uses conversation_id as thread_id for checkpointing
  • State is automatically loaded when conversation continues
  • All messages (HumanMessage, AIMessage, ToolMessage) are stored in checkpoints

Code Verification

Implementation Verification

This visualization is based on the actual implementation in backend/src/agents/workflow_agent.py:

  • Graph Creation: create_graph(checkpointer) creates StateGraph with 16 nodes (lines 1152-1271)
  • Entry Point: route_entry_node (line 62) routes based on patient_verified, history_shown, and new messages
  • Patient Verification Flow: extract_patient_info → validate_info → (ask_for_missing or verify_patient) → (create_patient or fetch_history) → show_history
  • Request Processing Flow: understand_request → validate_request → (ask_for_request_info or find_doctors) → (inform_no_doctors or rank_doctors) → create_tickets → confirm_booking
  • Checkpointer: PostgresSaver automatically saves state after each node execution (configured at line 1261)
  • LLM Initialization: ChatOpenAI initialized at line 50 with settings from config.py
  • Tool Calls: Tools are called via .invoke() method from nodes (e.g., line 158, 308, 369)

Workflow Execution Model

Execution Flow

The workflow executes in the following manner (based on actual code execution):

  • Sequential Execution: Nodes execute sequentially in a single invocation cycle via LangGraph StateGraph
  • Entry Routing: route_entry_node analyzes state and routes to first appropriate node
  • Conditional Routing: Each node sets next_action in state, routing functions determine next node
  • User Interaction Points: Workflow ends (waits for user) at ask_for_missing, show_history, ask_for_request_info (lines 1202, 1222, 1236)
  • Automatic Continuation: When user provides new message, route_entry detects it (line 78-82) and routes to appropriate node
  • State Recovery: State is automatically loaded from checkpointer when conversation continues (conversations.py line 131-138)
  • Checkpoint Saving: PostgresSaver checkpointer automatically saves state after each node (configured at compile time)
