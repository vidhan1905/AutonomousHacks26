Overview

This document describes the current LangGraph workflow-based agent system for the Hospital AI Assistant. The system uses a hybrid workflow pattern with explicit nodes for predictable execution, while maintaining conversational flexibility through LLM nodes.

Implementation: Based on backend/src/agents/workflow_agent.py with 17 explicit workflow nodes.

Key Features:

  • Hybrid workflow pattern: Explicit nodes for predictable execution
  • 17 workflow nodes: route_entry, fetch_history, show_history, understand_request, detect_complex_case, create_sequential_chain, route_to_next_doctor, collect_doctor_review, generate_final_summary, validate_request, ask_for_request_info, find_doctors, inform_no_doctors, rank_doctors, create_tickets, confirm_booking
  • Sequential review support: Complex cases use a single ticket that progresses through multiple doctors
  • LLM nodes for extraction, understanding, and formatting (9 nodes use LLM)
  • Tool nodes for database operations (6 nodes call tools)
  • PostgresSaver checkpointer for state persistence (automatic after each node)
  • LangSmith integration for observability and tracing

Execution Flow:

  1. Conversation API receives message → calls graph.ainvoke(initial_state, config)
  2. LangGraph Engine loads state from PostgresSaver checkpointer (if exists)
  3. Executes nodes sequentially based on routing logic
  4. Saves checkpoint after each node execution
  5. Returns final state with all messages

System Architecture

Architecture Overview

The system consists of multiple layers matching the actual implementation in workflow_agent.py:

  • Client Layer: Frontend React App → REST API Endpoints (FastAPI)
  • Application Layer: Conversation API (routes/conversations.py) → Workflow Agent (workflow_agent.py)
  • LangGraph Layer: StateGraph Engine with 17 workflow nodes, PostgresSaver Checkpointer for state persistence
  • Node Types:
    • LLM Nodes: show_history, understand_request, detect_complex_case, ask_for_request_info, inform_no_doctors, rank_doctors, confirm_booking, generate_final_summary
    • Validation Nodes: validate_request
    • Tool Nodes: fetch_history, create_sequential_chain, route_to_next_doctor, collect_doctor_review, find_doctors, create_tickets
  • Sequential Review: Complex cases use sequential review chain with single ticket progression
  • Tool Layer: Extraction Tools, Patient Tools, Doctor Tools, Ticket Tools (called from nodes)
  • LLM Services: ChatOpenAI (gpt-4o-mini) with Structured Output (Pydantic models)
  • Database Layer: PostgreSQL with patients, service_persons, tickets, conversations, checkpoints tables
  • Observability: LangSmith integration for tracing all LLM calls and workflow execution

Complex Case Detection

After understanding the request, the system detects if it's a complex case requiring multiple specialists:

  • Normal Case: Routes to standard flow (Validate → Find → Rank → Create Tickets → Confirm)
  • Complex Case: Routes to sequential review flow (Create Chain → Route to Next Doctor → Wait for Review → Collect Review → Route to Next Doctor → Repeat)

Sequential Review (Complex Case) Flow

Overview

For complex cases requiring multiple specialists, the system uses a sequential review chain where a single ticket progresses through multiple doctors in sequence. Each doctor reviews the case and provides notes that are visible to subsequent doctors.

Key Features:

  • Single Ticket: Only ONE ticket is created for the entire sequential review chain
  • Step Progression: The ticket progresses through sequential steps (Step 1, Step 2, Step 3, etc.)
  • Auto-Assignment: Steps are auto-assigned (no accept/reject for sequential review tickets)
  • Review Notes Accumulation: Review notes from completed steps are visible to subsequent doctors
  • UI Progress Tracking: The UI displays step progression and review notes from previous doctors

Sequential Review Process

  1. Detect Complex Case: LLM analyzes case and determines if multiple specialists are needed
  2. Create Sequential Chain: Creates SequentialReviewChain and SequentialReviewStep records
  3. Route to Next Doctor:
    • For first step: Creates a NEW ticket assigned to the first doctor
    • For subsequent steps: UPDATES the existing ticket by reassigning it to the next doctor
  4. Wait for Doctor Review: Doctor reviews the ticket and marks it as "completed" with review notes
  5. Collect Doctor Review: API endpoint calls submit_doctor_review to update step status and advance chain
  6. Route to Next Doctor: If more steps remain, ticket is reassigned to the next doctor
  7. Generate Final Summary: When all steps are complete, generate comprehensive summary

State Management Flow

State Persistence

The workflow uses PostgresSaver checkpointer for state persistence:

  • State is persisted after each node execution
  • Uses conversation_id as thread_id for checkpointing
  • State is automatically loaded when conversation continues
  • All messages (HumanMessage, AIMessage, ToolMessage) are stored in checkpoints

  • Sequential Review Flow: create_sequential_chain → route_to_next_doctor → (wait for review) → collect_doctor_review → route_to_next_doctor (repeat) → generate_final_summary
  • Checkpointer: PostgresSaver automatically saves state after each node execution (configured at line 1261)
  • LLM Initialization: ChatOpenAI initialized at line 50 with settings from config.py
  • Tool Calls: Tools are called via .invoke() method from nodes (e.g., line 158, 308, 369)

Workflow Execution Model

Execution Flow

The workflow executes in the following manner (based on actual code execution):

  • Sequential Execution: Nodes execute sequentially in a single invocation cycle via LangGraph StateGraph
  • Entry Routing: route_entry_node analyzes state and routes to first appropriate node
  • Conditional Routing: Each node sets next_action in state, routing functions determine next node
  • User Interaction Points: Workflow ends (waits for user) at show_history, ask_for_request_info
  • Automatic Continuation: When user provides new message, route_entry detects it and routes to appropriate node
  • State Recovery: State is automatically loaded from checkpointer when conversation continues (conversations.py line 131-138)
  • Checkpoint Saving: PostgresSaver checkpointer automatically saves state after each node (configured at compile time)
